# v5.0.0

<small>November 14, 2026 · [GitHub ↗](https://github.com/rapastranac/gempba/releases/tag/v5.0.0)</small>

A breaking release. gempba becomes one library with multithreading built in, plus an MPI component that a program asks for when it needs it, so the build-time flavors and their two namespaces are gone. Every rank calls one entry point, `scheduler::run`, and a run can be stopped early, from code, by a signal or from a dashboard, and says how it ended. The MPI component compiles against the MPI on the user's machine, the Java artifacts move to Maven Central, and the JARs' macOS native is Apple Silicon. Everything v4.3.0 deprecated is removed.

Upgrading needs code and build changes. C++ programs drop the `multithreading::` and `multiprocessing::` qualifiers and `GEMPBA_MULTIPROCESSING`; MPI programs include `<gempba/mpi.hpp>`, create their scheduler with `gempba::mpi::create_scheduler(topology)`, call `scheduler::run` on every rank and link `gempba::mpi` from `find_package(gempba COMPONENTS mpi)`. C programs use the unprefixed calls and `gempba_mpi.h`, and Java programs depend on `io.github.rapastranac:gempba` or `gempba-mpi`. `SIGINT` and `SIGTERM` now stop a run gracefully instead of killing it; `gempba::stop_on_signals(false)` keeps the old behavior. **Removed** and **Renamed** list every change with what to use instead.

**Removed**

- **The build-time flavors.** The `GEMPBA_MULTIPROCESSING` option and the compile definition it passed to consumers, the `gempba::multithreading` and `gempba::multiprocessing` namespaces, `find_package(gempba COMPONENTS mt)` and the rule that `mt` and `mpi` can't be used together are gone. Use `find_package(gempba)` and the calls in `gempba`, and add `COMPONENTS mpi` and `gempba::mpi` for MPI. Code that branched on `GEMPBA_MULTIPROCESSING` decides its mode itself (#414)
- **The build options `GEMPBA_DEV_MODE` and `GEMPBA_INSTALL_SHARED_ARTIFACTS`.** Nothing replaces them: the test hooks follow `GEMPBA_BUILD_TESTS`, and each install component ships only its own files. `GEMPBA_BUILD_MPI` replaces `GEMPBA_MULTIPROCESSING` in gempba's own build (see **Build**) (#414)
- **The installed MPI library.** `libgempba_mpi.a`, its CMake targets file and `gempba-mpi.pc` no longer install, since the MPI component installs as source (see **Changed**). An MPI program uses `find_package(gempba COMPONENTS mpi)`; no pkg-config file describes it. `gempba.pc` describes the core and no longer sets `-DGEMPBA_MULTIPROCESSING` (#415, #414)
- **The scheduler's center and worker views.** `scheduler::center`, `scheduler::worker`, `center_view()`, `worker_view()` and `worker::next_process()` are gone. Call `scheduler::run(node_manager, runnables, seed)` on every rank, with the seed on rank 0 only, and read `get_result()` and `get_all_results()` from `scheduler` on rank 0. `force_push` and `try_open_transmission_channel` move onto `scheduler`, and `create_load_balancer`, `create_node_manager` and `node_traits::delegate_remotely` take a `scheduler*` instead of a `scheduler::worker*` (#394)
- **The scheduler timeout,** ignored since v4.3.0. `create_scheduler(topology, timeout)` → `gempba::mpi::create_scheduler(topology)`, the C ABI's `gempba_scheduler_create(topology, timeout, out)` → `gempba_mpi_create_scheduler(topology, out)`, and Java's `GemPBA.createScheduler(topology, timeout)` → `io.gempba.mpi.Mpi.createScheduler(topology)` (#353, #414)
- **The v4.3.0 deprecations** (#373):
  - `telemetry_hub::set_worker_interval_ms()`, `worker_interval_ms()`, `latest_worker_frame()` and `control_kind::SET_WORKER_INTERVAL_MS`: use `set_interval_ms()`, `interval_ms()`, `latest_rank_frame()` and `SET_INTERVAL_MS`;
  - `telemetry_hub::set_node_interval_ms()`, which did nothing, and `node_interval_ms()`: node frames follow `set_interval_ms()` and `interval_ms()`;
  - the `set_worker_interval_ms` and `set_node_interval_ms` control lines, now dropped as unknown: send `{"kind":"set_interval_ms","value":N}`;
  - the `total_requested_tasks` stat, with `default_mpi_stats_visitor::m_total_requested_tasks` and its key in the C ABI's stats visit and Java's `RankStats`: read `coordinator_messages_handled` on the coordinator, and `sent_task_count` + `received_task_count` on workers.
- **The public telemetry transport.** `<gempba/telemetry/telemetry_transport.hpp>` no longer installs, and with it `telemetry_transport`, `worker_frame_sink`, `publish_worker` and `publish_final_worker`. v5.0.0 publishes no backend or transport interface, and `gempba::mpi` is its only backend. A custom scheduler still plugs in through `gempba::mpi::create_scheduler(std::unique_ptr<scheduler>)`, and gets telemetry over MPI (#414)
- **Java's `Scheduler.Center` and `Scheduler.Worker`,** with `Scheduler.center()` and `worker()`. Call `Scheduler.run(nm, runnables, seed, seedRunnableId)` on rank 0 and `run(nm, runnables)` on the other ranks, and read `getResult()` and `getAllResults()` from `Scheduler` on rank 0 (#394)

**Renamed**

- **MPI's calls are in `gempba::mpi`,** from `<gempba/mpi.hpp>` (#414):
  - `create_scheduler(topology)` and `create_scheduler(std::unique_ptr<scheduler>)` → `gempba::mpi::create_scheduler`;
  - `scheduler_topology`, `CENTRALIZED` and `SEMI_CENTRALIZED` → `gempba::mpi::scheduler_topology`, `gempba::mpi::CENTRALIZED` and `gempba::mpi::SEMI_CENTRALIZED`;
  - `get_default_mpi_stats_visitor()` → `gempba::mpi::get_default_mpi_stats_visitor()`;
  - `<gempba/defaults/default_mpi_stats_visitor.hpp>` → `<gempba/mpi/default_mpi_stats_visitor.hpp>`, which `<gempba/mpi.hpp>` includes. The class stays `gempba::default_mpi_stats_visitor`.
- **Every other call is in `gempba`, in all its forms** (#414, #394):
  - `multithreading::create_load_balancer(policy)` and `multiprocessing::create_load_balancer(policy, worker)` → `gempba::create_load_balancer(policy, scheduler = nullptr)`;
  - `multithreading::create_node_manager(lb)` and `multiprocessing::create_node_manager(lb, worker)` → `gempba::create_node_manager(lb, scheduler = nullptr)`;
  - the node factories (`create_explicit_node` and `create_lazy_node`, with and without serializers, and `create_from_bytes_node`) and `runnables::return_none` and `runnables::return_value` keep their names, in `gempba`.
- **Telemetry's C++ names say rank for a process,** as schema 2's keys already do; the JSON doesn't change (#373):
  - `worker_frame`, `worker_frame_header` and `worker_identity` → `rank_frame`, `rank_frame_header` and `rank_identity`;
  - `telemetry_hub::snapshot_worker_frame()` → `snapshot_rank_frame()`;
  - `m_worker_id` → `m_rank`, `m_worker_local_ms` → `m_rank_local_ms`, `m_idle_microseconds_per_worker` → `m_idle_microseconds_per_thread`, `m_sentinel_worker_id` → `m_sentinel_rank`, `m_dst_worker_id` → `m_dst_rank`, and the topology's `m_worker_ids` → `m_ranks`;
  - `MAX_WORKERS` → `MAX_RANKS`.
- **The C ABI drops the `mt` and `mp` prefixes** (#414, #394):
  - `gempba_mt_create_load_balancer` and `gempba_mp_create_load_balancer` → `gempba_create_load_balancer(policy, scheduler)`, and `gempba_mt_create_node_manager` and `gempba_mp_create_node_manager` → `gempba_create_node_manager(lb, scheduler)`, with a NULL scheduler in a multithreading program;
  - `gempba_mt_create_explicit_node` and `gempba_mp_create_explicit_node` → `gempba_create_explicit_node`, whose nodes can be sent to other ranks, and `gempba_mt_create_lazy_node` → `gempba_create_lazy_node`;
  - `gempba_scheduler_create` → `gempba_mpi_create_scheduler`, in `gempba_mpi.h` with `gempba_scheduler_topology_t`;
  - the `gempba_scheduler_center_*` and `gempba_scheduler_worker_*` calls and their `gempba_scheduler_center_t` and `gempba_scheduler_worker_t` handles → `gempba_scheduler_run`, `gempba_scheduler_is_root`, `gempba_scheduler_get_result` and `gempba_scheduler_visit_all_results`, on the scheduler itself, where `gempba_scheduler_barrier`, `gempba_scheduler_rank_me` and `gempba_scheduler_world_size` already were.
- **Java** (#414, #394):
  - `io.gempba.scheduler.SchedulerTopology` → `io.gempba.mpi.SchedulerTopology`, and `GemPBA.createScheduler` → `io.gempba.mpi.Mpi.createScheduler`;
  - `GemPBA.createLoadBalancer(policy, Scheduler.Worker)` and `createNodeManager(lb, Scheduler.Worker)` take the `Scheduler`.

**Changed**

- **One core library, with MPI as a component.** `libgempba` (`gempba::gempba`) holds the nodes, the node manager, the load balancers, the thread pool, the `scheduler` interface, telemetry and the C ABI; the MPI schedulers and MPI telemetry are the MPI component, `gempba::mpi`. One program can link both, and multithreading and MPI programs build side by side from one installation (#414)
- **libgempba is a shared library,** `libgempba.so.5` on Linux and `libgempba.dll` on Windows, where v4 installed `libgempba.a`. It exports only its public API. spdlog and fmt are compiled into it, and hwloc is a private dependency it loads at run time, so `find_package(gempba)` looks only for the threads library and a consumer compiles against only the C++ standard library, plus MPI for `gempba::mpi`. Programs load it at run time, from where the packages install it with hwloc's runtime (#414)
- **The MPI component compiles against your MPI.** It installs as source, and `find_package(gempba COMPONENTS mpi)` compiles it in your build into a static `gempba::mpi`, against the MPI CMake finds there: Open MPI, MPICH or MS-MPI. Before, each package's MPI part was compiled against one MPI and worked only with it. Your compiler must be compatible with the one that built libgempba, and switching MPIs takes another build directory, not a reinstall. A gempba build installs the component without MPI, and so does Homebrew; the apt and MSYS2 packages depend on an MPI (#415)
- **The packages keep their names, and each MPI package installs on top of its core package** (#414, #415, #438):
  - apt: `libgempba-dev` is the core and depends on hwloc's runtime, `libhwloc15`, instead of `libfmt-dev`, `libhwloc-dev` and `pkgconf`. `libgempba-mpi-dev` holds the MPI component's source and depends on `libopenmpi-dev (>= 4.0) | libmpich-dev`. Ubuntu 24.04's MPICH package starts every rank of a job alone ([Launchpad bug 2072338](https://bugs.launchpad.net/ubuntu/+source/mpich/+bug/2072338)), so use Open MPI there;
  - Homebrew: `gempba-mpi` depends on `gempba` from the same tap instead of conflicting with it, so both install together, and holds only the MPI component's source; `brew install open-mpi` or `mpich` for your build to compile it against. `gempba` installs only the core;
  - MSYS2: `mingw-w64-ucrt-x86_64-gempba` is the core and no longer depends on fmt or pkgconf; `mingw-w64-ucrt-x86_64-gempba-mpi` holds the MPI component's source and depends on MS-MPI.
- **One entry point on every rank.** `scheduler::run` throws `std::invalid_argument` if rank 0 passes no seed or another rank passes one, and `get_result()` and `get_all_results()` throw `std::logic_error` off rank 0; `is_root()` tells a rank whether it is rank 0. The built-in schedulers keep rank 0 as their coordinator, out of compute. A custom scheduler implements the protected `do_run`, `do_get_result` and `do_get_all_results`. Each rank reports its own `role_of(rank_me())` to telemetry at startup, so a role no longer has to be the same answer on every rank (#394)
- **`SIGINT` and `SIGTERM` stop a run gracefully by default,** in C++ and Java, instead of killing it (see **Added**). `create_node_manager` takes each of the two signals that nothing else handles yet, and `shutdown()` gives them back, so a program that installed its own handler first keeps it. A second Ctrl+C kills the process, while `SIGTERM` stays handled. `gempba::stop_on_signals(false)`, or Java's `GemPBA.stopOnSignals(false)`, keeps the signals' default. In Java, `GemPBA.createNodeManager` takes both through `sun.misc.Signal` instead of letting the JVM shut down, and a second `SIGINT` goes to the JVM's own handler (#465)
- **The Java artifacts are on Maven Central** as `io.github.rapastranac:gempba` (multithreading) and `io.github.rapastranac:gempba-mpi`, with no repository or token to configure. The Java packages stay `io.gempba`. `v4.1.0` to `v4.4.0` stay on GitHub Packages as `io.gempba:gempba` with the `mt` and `mp-mpi` classifiers, and GitHub Packages gets nothing from `v5.0.0` on. `build_jar_<os>.sh` installs into `~/.m2` under the new coordinates (#410, #470)
- **One Java API for both artifacts.** One `GemPBA` class serves both; `io.gempba.mpi` ships only in `gempba-mpi`, so MPI code doesn't compile against `gempba` (#414)
- **The JARs' macOS native is Apple Silicon only.** Each JAR holds exactly the `linux-x86_64`, `win-x86_64` and `osx-aarch64` natives, where `v4.3.0` and `v4.4.0` shipped `osx-x86_64`. On an Intel Mac, build the native from your version's tag with `bash scripts/build_jar_macos.sh MT` (or `MP`) and pass it with `-Dgempba.native.path=<checkout>/bindings/java/src/main/resources/natives/osx-x86_64/gempba_jni.dylib` (#409)

**Added**

- **Stopping a run early** (#465):
  - `gempba::request_stop()` asks the run to stop, from any thread, and returns at once. Nodes that haven't started are pruned, nodes already running finish their own work, and the run returns its best result so far, with its stats. The first stop wins until `gempba::shutdown()`;
  - `gempba::stop_requested()` says whether a stop was requested; long work inside one node can poll it and return early. A multithreading run, which has no `scheduler::run`, checks it after `wait()` and before `shutdown()`;
  - under MPI every rank stops, ranks that saw no signal too, and the run ends through the usual termination, result gathering and `MPI_Finalize`, without `MPI_Abort`;
  - `scheduler::run` returns a `gempba::run_outcome`, the same on every rank: `m_reason` (`end_reason::COMPLETED` or `INTERRUPTED`), `m_trigger` (`stop_trigger::NONE`, `CODE`, `SIGNAL` or `CONTROL`) and `m_signal`. A custom scheduler returns it from `do_run`, and `docs/telemetry/custom-schedulers.md` says what else it does on a stop;
  - C ABI: `gempba_request_stop()`, `gempba_stop_requested()`, `gempba_stop_on_signals()`, `gempba_request_stop_on_signal()` for a signal the host language caught itself, and `gempba_scheduler_run` fills a nullable `gempba_run_outcome_t*`;
  - Java: `GemPBA.requestStop()`, `GemPBA.isStopRequested()` and `GemPBA.stopOnSignals(boolean)`, and `Scheduler.run` returns an `io.gempba.value.RunOutcome` with `reason()`, `trigger()`, `signal()` and `isInterrupted()`.
- **A run says how it ended** (#465):
  - rank 0 logs one line: `gempba: run completed: the whole search space was explored, so the result is proven`, or a warning such as `gempba: run interrupted by SIGTERM: the result is the best one found before the stop, not a proven one`, likewise by `SIGINT (Ctrl+C)`, by `gempba::request_stop()` or from the dashboard. `scheduler::run` logs it, so custom schedulers get it too, and a run without a scheduler logs it in `shutdown()`;
  - the final telemetry line carries `end`: `{"reason":"completed"}`, or for example `{"reason":"interrupted","trigger":"signal","signal":"SIGTERM"}`. A stream that closes without a final line was lost: killed by `SIGKILL`, a crash or a node failure. The schema stays 2.
- **A dashboard can stop the run** with the control line `{"kind":"stop","token":"…"}`, accepted only when `token` matches the `GEMPBA_STOP_TOKEN` environment variable the run was started with; without that variable, every stop line is refused with a warning. Any user on the host can reach the telemetry socket, so the token keeps others from ending your run (#465)
- **Slurm jobs can end interrupted instead of lost.** A time limit sends `SIGTERM`, then `SIGKILL` after the cluster's `KillWait`, which may not leave the run time to wind down. Add `#SBATCH --signal=TERM@<seconds>`, with more seconds than your longest node takes, and start the ranks with `srun`, so every rank gets `SIGTERM` that long before the limit; `--signal=B:TERM@…` signals only the batch shell. `scancel --signal=TERM <jobid>` stops a job gracefully by hand (#465)
- **The JARs can load a native library you built.** `-Dgempba.native.path=<file>` loads that file instead of the bundled one, and fails if it names no file. `gempba-mpi`'s bundled native is built against Open MPI on Linux and macOS and MS-MPI on Windows; when it fails to load, the error keeps the OS's reason, names the MPI it was built against and points at `gempba.native.path` and the README's [Which MPI](https://github.com/rapastranac/gempba#which-mpi) section. The JNI build records that MPI in `gempba_jni.properties`, inside the JAR (#442)
- **`scripts/build_jar_host_linux.sh MT|MP` builds the JAR on a cluster, without Docker.** It builds the static hwloc the native links, with fmt's and spdlog's headers, builds `gempba_jni` against the host's compiler and MPI, prints the MPI it found and installs the JAR into `~/.m2`. Run it from the tag of your version, with a C++23 compiler, CMake, curl, Maven, a JDK and your MPI on `PATH`; it loads no modules (#446)

**Fixed**

- **Under the centralized MPI scheduler, rank 0's result could be empty** although a worker had found the best one: a worker's last improvement, found by its last task, was never proposed to rank 0. The worker now proposes its score once more before going idle, as the semi-centralized worker does (#433)
- **An MPI worker could take tens of seconds to see the termination message.** Both MPI schedulers probed one communicator until it was empty, so a backlog of score updates held the termination message back; they now take the communicators in turn (#465)
- **The quasi-horizontal balancer could run a branch twice, silently.** A running branch's deep `send` could hand that same branch to another thread, since it stayed `UNUSED` while it ran. Nodes are now `RUNNING` while their runnable executes (`node_state` gains `RUNNING`), and the balancer hands off only the leftmost root child still `UNUSED` (#456)
- **Submitting a node the balancer had already dispatched no longer throws `Node: N is already consumed`.** In both balancers, `try_local_submit` and `try_remote_submit` return true for a node already `PUSHED`, `SENT_TO_ANOTHER_PROCESS` or `DISCARDED`, as `forward` already skipped it (#456)
- **The quasi-horizontal balancer no longer throws `Attempted to access a null node` when it sends a root that still has children.** After pruning a node with no parent, it went on to correct the root of that node's missing parent; it now stops there, as the work-stealing balancer does (#459)
- **A new load balancer no longer reports a full pool.** For the first 100–200 µs, before its threads first went idle, a submission ran in the calling thread and counted as a pool-full rejection; both constructors now return once every thread is idle (#428)
- **Telemetry no longer slows each node's sentinel rank.** The sentinel rebuilt the hwloc topology on every node frame, on its scheduler thread: 94–131 ms per frame on a cluster, about a fifth of the thread's time at the default 500 ms interval, which showed as jagged CPU on the dashboard. It now loads the topology once per run (#454)
- **Multi-node MPI runs over UCX no longer end with `UCX WARN unexpected tag-receive descriptor ... was not matched`.** Rank 0 freed telemetry's communicator while a remote node's final node frame was still in flight; each sentinel now sends its node frame before its final rank frame (#447)
- **A run that can't listen on its telemetry port says so.** Rank 0 logs `telemetry can't listen on 127.0.0.1:<port> (<OS error>); this run has no telemetry stream. Pick another port with gempba::telemetry::configure_port.`, and the run goes on. Before, it went on with no stream and no message (#464)
- **On Windows, two runs no longer share a telemetry port.** The server's `SO_REUSEADDR` let a second run bind a port in use, so both logged `telemetry listening` and every client reached only one of them. It now uses `SO_EXCLUSIVEADDRUSE`, so the second run warns as above; Linux and macOS keep `SO_REUSEADDR`, which there only allows rebinding a port left in `TIME_WAIT` (#464)
- **`gempba-mpi` no longer crashes the JVM when MPI runs over UCX.** UCX puts its `SIGSEGV`, `SIGBUS`, `SIGILL` and `SIGFPE` handlers in front of the JVM's and took the JVM's own deliberate `SIGSEGV`s for crashes, so every rank died within seconds: with Open MPI on its UCX PML, as on InfiniBand and RoCE clusters, and with MPICH over UCX, as Debian's is. On Linux, the native library now gives the JVM its handlers back; C++ programs keep UCX's (#443)
- **Java runs no longer crash with a `SIGSEGV` in `gempba_create_explicit_node`.** The garbage collector could free a short-lived parent node, such as a dummy node, while native code was still copying it; the child factories and `Node.getResult` now keep it reachable (#452)
- **`gempba_scheduler_destroy` followed by `gempba_shutdown` deleted the scheduler twice.** `gempba_scheduler_destroy` now frees only the handle (#414)

**Build**

- `GEMPBA_BUILD_MPI`, on by default when gempba is the top-level project and off as a subproject, compiles the MPI component in gempba's own build, for its tests and the Java native, and needs MPI. Installs ship the component's source either way, so `-DGEMPBA_BUILD_MPI=OFF` builds and installs everything without MPI (#414, #415)
- gempba's CMake build has one directory per component, `src/core` and `src/mpi`, each declared with one `gempba_add_component()` call from `cmake/gempba_component.cmake`. `find_package` loads each requested component through its installed `gempba-<component>.cmake`. The targets, options and installed files don't change (#436)
- `bindings/jni/build_deps.sh` builds only hwloc's library and headers, not its command-line tools, so it no longer fails on hosts whose ncurses those tools can't link (#446)
- macOS CI runs on Apple Silicon, and only on pushes to and pull requests into `main` and `release`, on `v*` tags and by manual run. The fat-JAR job fails unless each JAR holds exactly the three natives, and the Homebrew formulas are installed and tested on arm64 (#409)

**Docs**

- The README describes the core and the MPI component: how each package installs, `find_package(gempba COMPONENTS mpi)`, the MPI requirement, and macOS as `aarch64` (Apple Silicon). Its Java section gives the Maven Central dependency and a **Which MPI** section on building `gempba_jni` against another MPI (#414, #415, #409, #410, #442)
- Setting the telemetry port needs only `<gempba/gempba.hpp>`: call `gempba::telemetry::configure_port(9001);` before the first `create_*` call, as for `gempba::telemetry::enable()` and `disable()`; the default stays 9000. The C ABI's `gempba_telemetry_configure_port` and Java's `GemPBA.configureTelemetryPort` match it. No API changed: a test pins that the main header reaches it (#458)
- `docs/telemetry/wire-format.md` documents the final line's `end`, the `stop` control line and the two dropped control lines (#465, #373)
- `docs/telemetry/custom-schedulers.md` says what a custom scheduler implements for `scheduler::run` and what it does on a stop (#394, #465)
- The Javadoc names the `gempba` and `gempba-mpi` artifacts instead of the `mt` and `mp-mpi` JARs (#470)

**Not in this release**

- **gempba isn't in MSYS2's own repository yet.** Install the `.pkg.tar.zst` files from the GitHub Release with `pacman -U`, as before; `pacman -S` from MSYS2's UCRT64 repository follows after `v5.0.0` (#413)
